# DevOps Interview Topics — Priority 1

## 1. DevOps Fundamentals

### 1. What is DevOps?

**Definition:**  
DevOps is a combination of **development practices, operations practices, automation, and culture** that enables teams to build, test, deploy, and maintain software **faster and more reliably** through collaboration and automation.

**Interview Answer:**  
> “DevOps is a set of practices and a culture that brings Development and Operations teams together to automate and streamline the software development and delivery process. Its main goal is to achieve faster, reliable, and continuous software delivery.”

---

### 2. Development vs Operations

**Definition:**  
- **Development (Dev):** Responsible for designing, coding, and testing applications.
- **Operations (Ops):** Responsible for deploying, managing, monitoring, and maintaining applications and infrastructure.

**Interview Answer:**  
> “Development focuses on building and testing the application, while Operations focuses on deploying, running, monitoring, and maintaining it. DevOps brings both teams together to improve collaboration and automate the software delivery process.”

---

### 3. Why DevOps?

**Definition:**  
DevOps is used to **reduce the gap between Development and Operations**, automate repetitive tasks, accelerate software delivery, and improve reliability.

**Interview Answer:**  
> “DevOps is needed to reduce the gap between development and operations, automate the software delivery process, release software faster, improve collaboration, and increase reliability.”

---

### 4. Benefits of DevOps

**Definition:**  
The major benefits of DevOps include **faster delivery, automation, improved collaboration, continuous feedback, higher reliability, and faster recovery from failures.**

**Interview Answer:**  
> “The major benefits of DevOps are faster software delivery, automation of repetitive tasks, better collaboration between teams, improved software quality and reliability, continuous feedback, and faster recovery from failures.”

---

### 5. DevOps Lifecycle

**Definition:**  
The DevOps lifecycle is a continuous process involving stages such as:

**Plan → Code → Build → Test → Release → Deploy → Operate → Monitor → Feedback**

**Interview Answer:**  
> “The DevOps lifecycle is a continuous cycle that includes planning, coding, building, testing, releasing, deploying, operating, and monitoring applications. Feedback from monitoring is used to improve the next development cycle.”

---

### 6. Continuous Integration (CI)

**Definition:**  
Continuous Integration is the practice of **frequently integrating code changes into a shared repository and automatically building and testing them.**

**Interview Answer:**  
> “Continuous Integration means developers frequently merge their code into a shared repository, where automated builds and tests are performed to detect integration problems early.”

---

### 7. Continuous Delivery

**Definition:**  
Continuous Delivery is the practice of **automatically preparing validated code for release so that it can be deployed to production when required.**

**Interview Answer:**  
> “Continuous Delivery automatically builds, tests, and prepares the application for release. The application is always kept in a deployable state, but production deployment usually requires a manual approval or trigger.”

---

### 8. Continuous Deployment

**Definition:**  
Continuous Deployment is the practice of **automatically deploying successfully tested code to production without requiring manual approval.**

**Interview Answer:**  
> “Continuous Deployment automatically deploys code to production after it passes the required automated tests and checks, without manual approval.”

---

### 9. CI/CD Pipeline

**Definition:**  
A CI/CD pipeline is an **automated sequence of processes used to build, test, package, and deploy software.**

**Interview Answer:**  
> “A CI/CD pipeline is an automated workflow that takes code from development through stages such as build, testing, artifact creation, and deployment. It helps deliver software consistently and efficiently.”

**Typical flow:**  
`Code → Build → Unit Test → Integration Test → Artifact → Deploy → Monitor`

---

### 10. DevOps Culture and Collaboration

**Definition:**  
DevOps culture promotes **collaboration, shared responsibility, communication, automation, continuous feedback, and continuous improvement** between development, operations, security, and other teams.

**Interview Answer:**  
> “DevOps culture means teams share responsibility for delivering and operating software. It emphasizes collaboration, communication, automation, continuous feedback, and continuous improvement rather than working in isolated teams.”

---

### 11. Agile vs DevOps

**Definition:**  
- **Agile:** Software development methodology focused on **iterative development, customer feedback, and adaptability**.
- **DevOps:** Practices and culture focused on **collaboration, automation, integration, and continuous software delivery**.

**Interview Answer:**  
> “Agile primarily focuses on iterative software development and responding quickly to changing requirements, while DevOps extends collaboration across development and operations and focuses on automating and continuously delivering software.”

---

### 12. SDLC vs DevOps

**Definition:**  
- **SDLC:** Defines the overall phases involved in developing software.
- **DevOps:** Adds collaboration, automation, continuous integration, delivery, deployment, monitoring, and feedback across the software lifecycle.

**Interview Answer:**  
> “SDLC is a framework that defines software development phases such as requirements, design, development, testing, deployment, and maintenance. DevOps complements the SDLC by introducing automation, collaboration, CI/CD, continuous monitoring, and continuous feedback.”

---

# 2. Git & GitHub

### 13. What is Git?

**Definition:**  
Git is a **distributed version control system** used to track changes in source code and allow multiple developers to collaborate.

**Interview Answer:**  
> “Git is a distributed version control system used to track changes in source code, maintain different versions of a project, and enable developers to collaborate efficiently.”

---

### 14. Git vs GitHub

**Definition:**  
- **Git:** Version control software that runs locally and manages code history.
- **GitHub:** A cloud-based platform for hosting Git repositories and enabling collaboration.

**Interview Answer:**  
> “Git is the version control system used to track and manage code changes, while GitHub is a platform that hosts Git repositories and provides collaboration features such as pull requests, issues, and code reviews.”

---

### 15. Git Repository

**Definition:**  
A Git repository is a location that contains the **project files and their complete version-control history**, including commits, branches, and configuration.

**Interview Answer:**  
> “A Git repository is a storage location for a project where Git tracks files, commits, branches, and the history of changes.”

---

### 16. Working Directory

**Definition:**  
The working directory is the **current filesystem area where the project files are checked out and where developers make changes.**

**Interview Answer:**  
> “The working directory is the local copy of the project where I create, modify, or delete files before staging those changes for a commit.”

---

### 17. Staging Area

**Definition:**  
The staging area is an **intermediate area where selected changes are placed before they are committed.**

**Interview Answer:**  
> “The staging area allows me to select which changes should be included in the next commit. I use `git add` to move changes from the working directory to the staging area.”

---

### 18. Commit

**Definition:**  
A commit is a **snapshot of staged changes stored in Git's version history** with a unique identifier.

**Interview Answer:**  
> “A commit is a saved snapshot of staged changes in the Git repository. It represents a specific point in the project's version history.”

---

### 19. Branch

**Definition:**  
A branch is an **independent line of development** that allows developers to work on features or fixes without directly modifying another branch.

**Interview Answer:**  
> “A branch is an independent line of development in Git. It allows developers to work on features or bug fixes separately and later merge those changes into another branch.”

---

### 20. Merge

**Definition:**  
Merge is the process of **combining changes from one branch into another branch.**

**Interview Answer:**  
> “Git merge combines the changes from one branch into another branch. For example, I can merge a feature branch into the main branch after the feature is completed and reviewed.”

---

### 21. Pull Request

**Definition:**  
A Pull Request, or PR, is a request to **review and merge changes from one branch into another repository branch**, commonly on platforms such as GitHub.

**Interview Answer:**  
> “A Pull Request is a mechanism used to propose changes from one branch to another. It allows team members to review, discuss, test, and approve the changes before merging them.”

---

### 22. Clone

**Definition:**  
Clone means creating a **local copy of a remote Git repository**, including its files and version history.

**Interview Answer:**  
> “Git clone downloads a remote repository to my local machine, including its files, branches, and Git history, so I can work on the project locally.”

---

### 23. Fork

**Definition:**  
A fork is a **personal copy of another user's repository under your own account on a Git hosting platform.**

**Interview Answer:**  
> “A fork creates a copy of someone else's repository under my own GitHub account. It is commonly used when I want to make changes to a repository without having direct write access to the original repository.”

---

### 24. Push

**Definition:**  
Push means **uploading local commits to a remote repository.**

**Interview Answer:**  
> “Git push sends my local commits to a remote repository, such as GitHub, so that the changes are available to other collaborators.”

---

### 25. Pull

**Definition:**  
Pull means **fetching changes from a remote repository and integrating them into the current local branch.**

**Interview Answer:**  
> “Git pull retrieves changes from the remote repository and integrates them into my current local branch.”

---

# 3. Git Commands

### 26. `git init`

**Definition:**  
Initializes a **new Git repository** in the current directory.

**Interview Answer:**  
> “`git init` initializes a new Git repository in the current directory and creates the Git metadata required for version control.”

---

### 27. `git add`

**Definition:**  
Moves changes from the **working directory to the staging area**.

**Interview Answer:**  
> “`git add` stages selected changes so they can be included in the next commit.”

**Example:**
```bash
git add file.txt
```

---

### 28. `git commit`

**Definition:**  
Creates a **new commit containing the staged changes**.

**Interview Answer:**  
> “`git commit` creates a snapshot of the changes currently present in the staging area and stores it in the Git history.”

**Example:**
```bash
git commit -m "Added login feature"
```

---

### 29. `git push`

**Definition:**  
Uploads local commits to a **remote repository**.

**Interview Answer:**  
> “`git push` uploads my local commits to the configured remote repository.”

**Example:**
```bash
git push origin main
```

---

### 30. `git pull`

**Definition:**  
Fetches changes from a remote repository and **integrates them into the current branch**.

**Interview Answer:**  
> “`git pull` retrieves changes from a remote repository and integrates them into my current local branch.”

**Example:**
```bash
git pull origin main
```

---

### 31. `git clone`

**Definition:**  
Creates a **local copy of a remote repository**.

**Interview Answer:**  
> “`git clone` copies a remote Git repository to my local machine so I can work with the project locally.”

**Example:**
```bash
git clone https://github.com/user/project.git
```

---

### 32. `git branch`

**Definition:**  
The `git branch` command is used to **create, list, rename, or delete branches**.

**Interview Answer:**  
> “`git branch` is used to manage branches in Git. I can use it to list existing branches or create and delete branches.”

**Examples:**
```bash
git branch
git branch feature-login
git branch -d feature-login
```

---

### 33. `git merge`

**Definition:**  
Combines the changes from one branch into the **currently checked-out branch**.

**Interview Answer:**  
> “`git merge` combines the changes from a specified branch into my current branch.”

**Example:**
```bash
git checkout main
git merge feature-login
```

---

# 4. Git Concepts

### 34. Merge Conflicts

**Definition:**  
A merge conflict occurs when Git **cannot automatically combine changes**, usually because different branches modify the same part of a file incompatibly.

**Interview Answer:**  
> “A merge conflict occurs when Git cannot automatically determine which changes to keep. I resolve it by reviewing the conflicting sections, choosing or combining the correct changes, then staging and committing the resolved file.”

**Typical process:**
```text
Merge
  ↓
Conflict
  ↓
Resolve manually
  ↓
git add
  ↓
git commit
```

---

### 35. `.gitignore`

**Definition:**  
`.gitignore` is a configuration file that specifies **files and directories Git should intentionally ignore when detecting untracked files.**

**Interview Answer:**  
> “`.gitignore` tells Git which files or directories should not normally be tracked. It is commonly used for sensitive files, temporary files, build outputs, logs, and dependency directories.”

**Example:**
```text
.env
node_modules/
*.log
__pycache__/
```

---

### 36. Git Workflow

**Definition:**  
Git workflow is the process developers follow to **create or modify code, stage changes, commit them, push them, review them, and merge them** into the appropriate branch.

**Interview Answer:**  
> “A typical Git workflow is to clone or create a repository, create a feature branch, modify the code, stage the changes using `git add`, commit them using `git commit`, push the branch to the remote repository, create a Pull Request for review, and merge it after approval.”

**Typical workflow:**
```text
Clone Repository
      ↓
Create Branch
      ↓
Modify Code
      ↓
git add
      ↓
git commit
      ↓
git push
      ↓
Pull Request
      ↓
Code Review
      ↓
Merge
```
